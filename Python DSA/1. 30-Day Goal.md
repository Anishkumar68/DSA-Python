# 30-Day Goal

By the end of the month, aim to be able to:

- Solve programming problems systematically.
    
- Break large problems into smaller pieces.
    
- Write cleaner, more maintainable code.
    
- Understand core data structures and algorithms.
    
- Debug instead of guessing.
    
- Build one small real-world project.
    
- Explain your technical decisions clearly.
    
- Develop the habit of thinking like an engineer.

### Rule for every problem

Before writing code, force yourself to answer:

1. What exactly is the problem?
    
2. What are the inputs?
    
3. What should the output be?
    
4. What are the edge cases?
    
5. What is the simplest solution?
    
6. Can I make it faster?
    
7. What is the time/space complexity?
    

**Don't immediately look at the solution.** Give yourself 20–30 minutes first.

10. [ ] Graphs
11. [ ] Greedy Algorithms
12. [ ] Dynamic Programming
13. [ ] Bit Manipulation
14. [ ] Tries
15. [ ] Sliding Window & Two Pointers

Your target:

**2–4 problems/day**, but prioritize understanding over quantity.

For every problem you get wrong, create a small note:

> **Problem → Why I failed → Correct idea → Pattern**

After a few weeks you'll start recognizing:

> "This looks like a sliding-window problem."

rather than:

> "I have no idea how to solve this."

That pattern recognition is one of the biggest improvements you can make.

**Theme: Stop thinking only about algorithms. Start thinking about systems.**

|Day|Focus|
|---|---|
|15|OOP principles|
|16|SOLID + clean code|
|17|REST APIs|
|18|Databases + SQL|
|19|Authentication + authorization|
|20|Git + branching + code review|
|21|🧪 Design/debugging challenge|

Spend more time **building** this week.

For example, if you're building a backend:

```text
Client
   ↓
API
   ↓
Controller
   ↓
Service
   ↓
Database
```

Learn to ask:

- Where should this logic live?
    
- What happens if the database fails?
    
- What happens with invalid input?
    
- How do I prevent duplicate data?
    
- How would this behave with 10 users?
    
- What changes if there are 100,000 users?
    

These questions develop engineering thinking.

🚀 Final engineering challenge:

Pretend another developer will maintain your project.

Ask yourself:

- Is the code readable?
    
- Are functions too large?

Then fix the **5 biggest problems** you find.

# 🧠 Your daily logical-thinking exercise

Do this **every day for 20–30 minutes**.

Rotate between:

**Monday:** Number/pattern problems  
**Tuesday:** Algorithm problem  
**Wednesday:** Debug broken code  
**Thursday:** SQL problem  
**Friday:** System-design question  
**Saturday:** Coding challenge  
**Sunday:** Review mistakes

The important part is not solving hundreds of problems.

It's developing this mental process:

```text
Problem
   ↓
Understand
   ↓
Break into pieces
   ↓
Find pattern
   ↓
Create solution
   ↓
Test edge cases
   ↓
Analyze complexity
   ↓
Implement
   ↓
Debug
   ↓
Refactor
```

## 🚫 Avoid this during the month

Don't spend 3 hours doing:

> Tutorial → Tutorial → Tutorial → Tutorial

without building anything.

Use roughly:

**30% learning + 70% doing.**

And when stuck, follow:

**Try → Think → Write down what you know → Search/documentation → Try again → Then look at solution.**
